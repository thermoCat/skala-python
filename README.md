# 데이터 수집 미니 파이프라인

Open-Meteo(서울 3일 시간대별 기온·강수확률), countries.dev(한국 국가 정보), ip-api(IP 기반 지역 정보)
3개 API를 비동기로 동시 수집하고, Pydantic v2로 스키마를 검증한 뒤 CSV/Parquet 두 형식으로 저장하며
읽기·쓰기 성능을 비교하는 파이프라인입니다.

## 폴더 구조

```
.
├── main.py              # 실행 진입점
├── pipeline/
│   ├── config.py         # API URL, 저장 경로 등 상수
│   ├── collector.py       # httpx + asyncio.gather 비동기 수집
│   ├── schemas.py         # Pydantic v2 모델 + 검증
│   ├── storage.py         # CSV/Parquet 저장 및 성능 비교
│   └── main.py             # 파이프라인 orchestration
├── tests/                # pytest 테스트
└── data/                 # 저장 결과물 (git에는 포함 안 됨)
```

## 실행 방법

Python 3.11 이상이 필요합니다 (`pyproject.toml`의 ruff `target-version` 기준).

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt

python main.py      # 파이프라인 실행
pytest -v           # 테스트 실행
ruff check .         # 린트 검사
```

## Code 분석에 대한 의견

데이터 수집 파이프라인은 비동기 수집 → 스키마 검증 → 저장/성능 비교라는 흐름을 파일별로 분리하여, 하나의 파일이 많은 책임을 갖지 않도록 구성했음.

공통 로직을 함수로 추출해 API/스키마를 반복문과 호출로 처리하여, API가 하나 더 추가되더라도 기존에 구성해놓은 함수를 그대로 재사용할 수 있는 구조임.

Pydantic 필드마다 주석을 달아, 단순히 타입만 맞으면 통과하는 게 아니라 물리적/정의적 범위를 검증 기준으로 삼아 더 정확한 검증이 가능하도록 함.

Parquet은 처음 호출해서 읽을 때 콜드스타트처럼 캐시에 올라가는 데 시간이 걸리는데, 3번씩 읽어서 평균을 도출하니 훨씬 빨라짐 — 1회(콜드스타트), 3회 평균 결과를 함께 로깅함.

### 추가 의견

**네트워크 끊김 시 재시도 로직**
`collector.py`의 `_fetch_json`은 실패 시 바로 예외를 던지고 종료함. 실제 운영되는 서비스라면 재시도 로직을 추가하는 게 안정성 측면에서 고려해볼 사항임.

**부분 실패 처리 방식**
`parse_weather`에서 72건의 데이터 중 1건이라도 검증이 실패하면 데이터 전체가 예외로 종료됨. 현재는 하나의 데이터라도 실패하면 신뢰할 수 없는 데이터라는 전제하에 설계되었는데, 실제 운영되는 서비스에서는 잘못된 레코드만 스킵하면서 로그만 남긴 후 계속 처리하는 방식도 고려 가능할 것 같음.

**데이터의 최신성 검증**
스키마 검증은 타입과 범위만 확인할 뿐, 값이 실제로 최신인지는 검증하지 않음(예: population 통계가 몇 년 전 값이어도 통과). 응답을 받은 시각을 타임스탬프로 남기더라도 이는 우리가 언제 수집했는지를 기록하는 것일 뿐이고, countries.dev나 ip-api 응답에는 데이터 자체가 마지막으로 갱신된 시점이 포함되어 있지 않아 진짜 신선도는 검증할 수 없음. 필요하다면 API가 갱신 시점 필드를 제공하는지 먼저 확인하고, 없다면 수집 시각만이라도 별도로 기록해 감사 추적(lineage) 용도로 활용하는 방식을 고려할 수 있음.
